CodeIsland Buddy — Taking Companion-First Further

The identity call is made and the first build is live: Buddy is a coding-agent companion, and the 19-module hub is trimmed to 7 keepers behind a reversible flag. That build was pure subtraction. The through-line for what comes next: subtraction bought focus; now spend it. Three kinds of spending, in order: finish the promises the flag already makes (the hero, the two catalog leaks, the sparse-rack problem), give the freed surface something only Buddy can show (an agent ledger, blocked-agent escalation, verbs on the lock screen), and convert reversible into deleted only when real use has voted. Eight moves below, ranked, each grounded in the code as it sits on claude/buddy-companion-first this morning.

What shipped overnight (verified against the diff, not the plan): commit e69ae32, 4 files, +69/-7, reversible behind buddy.companionFirst.v1 (default on) with a "Companion-first Tools" toggle in the presence menu.
  • CompanionFirst.swift (new, 54 lines): the 7-keeper set, PersonalHubSnapshot.filteringModules, and a filteredCatalog helper.
  • RemoteApprovalClient.swift: ingest-layer filter on refreshHub and the mock path; unset mode now defaults to .code.
  • Nothing deleted; CodeIslandCore untouched. Known leftovers: the quiet-hero rework (B2-13) is not done, the rack editor and App Intents still enumerate all 19, and no Mac rack holds all 7 keepers, so a stored Home mode renders a near-empty Tools grid. The tab restructure (B2-12) stays deferred.

Finish the quiet hero the trim already half-rewrote

Effort SImpact HighFinishes B2-13 (accepted, building)

The overnight filter already gutted that hero by side effect: reminders and weather no longer arrive in the snapshot, so the reminders row and the weather subtitle silently vanish, leaving calendar plus agents, still calendar first. The app decided it is about agents; its quiet home screen has not been told deliberately, only by subtraction.

Next action Reorder in CompanionTodayTimeline: agents row first (the module summary is already reused as idleSummary at :725-728, so the data path exists), calendar second with its Join button demoted to row level, and the headline subtitle drawn from the agents summary in the idle case instead of "Next: meeting". Ship behind the same flag. This is a one-view change; move 4 later upgrades what the agents row can say.

MOVE 2

Close the two catalog leaks: rack editor and Siri

Effort SImpact MediumIntegrity of the flag

Insight CompanionFirst.filteredCatalog(_:) was written for exactly this and currently has zero call sites. The rack editor offers all 19 modules to add back (availableModules, PersonalHubView.swift:878-880), and Shortcuts/Siri expose the full catalog through CodeIslandIntentModule (CodeIslandAppIntents.swift:28-31), so "Open CodeIsland Module: Teleprompter" deep-links into a module the app claims not to have. Two call sites, plus one UI test asserting a cut module cannot be reached while the flag is on.

MOVE 3

Solve sparse racks on the wire, not the client

Effort MImpact Very highMac + iOS + web

Insight Racks are Mac-side, persisted per mode (PersonalHubConfigurationStore), and the snapshot request carries only requestedMode (PersonalHubProtocol.swift:741-755). No rack contains all 7 keepers: the code rack is 5 of them plus downloads and windowManager, while calendar and notifications live only in the work and home racks (PersonalHubProtocol.swift:820-831). So the client-side filter can never show the full keeper set, and a stored Home mode filters down to a one-module grid that reads as breakage. The question posed overnight (define a cross-rack keeper view Mac-side, or coerce mode?) has a clear answer: coercion is a bandage, the keeper view belongs on the wire.

Next action Additive wire change, same pattern that carried the R3 risk field: an optional requestedModules: [PersonalHubModuleID]? on PersonalHubSnapshotRequest; when present, the Mac composes exactly those modules across racks in PersonalHubService. Old Macs ignore the unknown key and the client filter still applies, so it degrades to today's behavior. Under the flag, hide the Home/Work/Code mode strip (PersonalHubView.swift:654) and present one Companion rack. Interim, this week: a two-line coercion of a stored non-code mode to .code at launch when the flag is on, accepting the missing calendar/notifications for days, not weeks. Server-side composition also means the web approval surface (RemoteApprovalWebApp) and any second device inherit the trim for free, which the per-device UserDefaults flag never can.

MOVE 4

The away ledger: what shipped while you were gone

Effort MImpact Very highMakes the trim a feature

Insight So far companion-first only makes Buddy smaller. The positive case is the thing no other app on the phone can know: what your agents did while you were away. Today the agents module carries live sessions only (PersonalHubService.swift:1264 onward, first 6, "N total sessions"); there is no completion history anywhere on the wire, so "All clear" is always amnesiac. The Mac already observes every session start, status change, and end through the hook pipeline; it just forgets them.

Next action Mac-side ring buffer of session transitions (project, agent, outcome, timestamp; last ~50) fed from the hook events AppState already receives, exposed either as a second items section on the agents module or as a small activity payload on the same snapshot. Buddy stores a lastOpenedAt and renders the diff: "Shipped 1.0.62, 22m ago. rgos tests passed, 1h ago. 2 still running." This slots directly into move 1's hero as row one, becomes the data layer for B2-12's Activity tab before any tab restructure happens, and gives cross-session roll-ups a home. Build the data first, the tab later.

MOVE 5

Put the verb where the alert is (B2-15, now urgent)

Effort MImpact Very highWatch + LA + Dynamic Island + notifications

Insight Carrying companion-first to the glanceable ring is not a trimming job: the Watch, Live Activity, Dynamic Island, StandBy, and widgets are already agent-only (WatchContentView has zero hub code; the LA widget renders sessions and mascots). Out there the gap is capability, not content. Every notification is tap-to-open (no UNNotificationCategory registered anywhere; CompanionAppDelegate.swift:59-66 only routes to launch), the Live Activity has .widgetURL deep links but no Button(intent:), and the Watch approves but tells you to "Answer on iPhone" for questions. Now that Buddy's identity is settled as "act on your agents from anywhere", B2-15 stops being one proposal among six and becomes the single highest-leverage unbuilt item.

Next action Three additions that all preserve the content-free APNS design (an action triggers the same authenticated fetch-then-act the app runs on open): register approve/deny/answer notification categories in CompanionAppDelegate; add Button(intent:) to CodeIslandLiveActivityWidget.swift; let the Watch answer questions (WatchContentView.swift:405). Coordinate with the in-flight secure-approval-sheet plumbing rather than duplicating it, per the Batch 02 scope note.

MOVE 6

Escalate on blocked, not just notify once

Effort MImpact HighRides one payload rev with B2-03 risk

Insight Buddy announces a need once and goes quiet. An approval that sits for 25 minutes while you are at lunch costs exactly one buzz, the same as one that gets handled in 10 seconds; the product treats a stalled agent and a handled one identically after the first push. Waiting-age exists nowhere in CompanionStatePayload, and B2-03 already established that the same payload needs a risk field. Two fields, one payload revision.

Next action Add risk and waitingSince to the companion state payload in one rev. Then: time-sensitive re-notification at thresholds (5 and 15 minutes, configurable), waiting-age rendered in the Live Activity and the move 1 hero ("Codex waiting 12m"), and a hard dependency on B2-16 so "waiting 20m" is never shown when the truth is "Mac unreachable for 20m". This is the away-from-desk moment the whole product exists for; it should be the loudest thing Buddy ever does, and the only loud thing.

MOVE 7

Staged deletion of the 12, gated on evidence

Effort M, spreadImpact Medium, risk-reducingDo not rush this

Insight Three load-bearing couplings hide inside the cut set, all found in the code this morning. First, the Capture flow (a keeper) writes through cut modules' action endpoints: quick-jot posts reminders.add and notes.add (PersonalHubView.swift, preparePendingQuickJot). Second, rack persistence itself rides a cut module: quickToggles.setModeRack (PersonalHubService.swift:141, :516). Third, the Mac-side services also feed the Mac's own surfaces and the web app (GlancesView renders weather natively; PersonalHubMacView shows the catalog), and the Buddy decision never covered those. The lesson: cut modules are not the same as cut verbs or cut services. The nexus test judged phone surfaces; some actions underneath them deserve to survive as capture verbs.

Next action

  • Stage 0, now: count module opens and toggle flips locally (a UserDefaults tally is enough). Set a decision date, two weeks out, so reversible does not become permanent limbo.
  • Stage 1, after the window: move the filter server-side (move 3), so Buddy snapshots stop composing the 12 at the source. Mac services keep running for Mac surfaces.
  • Stage 2: re-home setModeRack to a neutral config action; decide whether quick-jot task/note survive as capture verbs under shelf (recommended) or die with their modules. Then delete the iOS module-card branches for the 12.
  • Stage 3: delete phone-side module clients and Mac services with no remaining consumer: TeleprompterWindowController (363 lines), WindowManagerController (124), BluetoothDeviceController (15), the camera preview path, plus their strings across all 7 locales. Check first that Buddy's NSCameraUsageDescription and NSBluetoothAlwaysUsageDescription are not load-bearing elsewhere: CompanionBluetoothCentral is pairing transport, not the bluetooth module, and dictation keeps the mic string. Shrinking the privacy manifest of a Developer Tools app is a real App Store win.
  • Never (for now): removing PersonalHubModuleID cases. Persisted configurations decode against the enum; retire IDs only at a deliberate protocol version bump.

Risks to watch in real use

  1. Default-on hides the cost of being wrong. You only notice a cut module when you reach for it and miss. Without a decision date and the stage-0 counters, the two-week test never concludes and 19 modules get maintained behind a flag forever.
  2. Sparse Tools reads as breakage today. Until the interim coercion or move 3 lands, a stored Home mode shows a one-module grid under a Home/Work/Code strip that implies choice it no longer delivers. First impressions of the flag will be formed here.
  3. The app currently disagrees with itself. Siri and the rack editor still offer the full catalog while Tools hides it (move 2). Small surface, but it undermines the claim that the trim is the product's identity rather than a display setting.
  4. The quiet hero can now feel empty. With reminders and weather gone, a meeting-free day leaves the hero with little to say until the ledger (move 4) exists. Watch whether "All clear" plus the agents summary carries the screen or reads as a blank app.
  5. Capture is quietly coupled to cut modules. Quick-jot writes through reminders and notes actions; a careless stage-2 deletion breaks a keeper feature. The staged plan exists precisely for this.
  6. Per-device flag drift. The UserDefaults flag lives on one phone. A second device, the web surface, and the Mac's own Tools all still show the old world until the keeper set moves server-side.
  7. Escalation can become noise. Moves 5 and 6 add louder verbs; without B2-16's reachability truth and sane thresholds, Buddy could nag about an unreachable Mac and burn the trust the trim just bought.

Sequence

This week, finish what the flag promises: moves 1 and 2 plus the two-line mode coercion (all S, all inside the existing flag), and start the stage-0 counters with a decision date two weeks out. Then land B2-14's token file so every new surface after it is built on the system, not against it. Next block: move 3's wire change and move 4's ledger together (one Mac-side PR, one iOS PR; they share the snapshot), followed by the single payload rev that powers moves 5 and 6, with B2-16's reachability truth landing alongside so the new loudness never lies. Hold B2-12's tab restructure until the ledger is real and you are in the loop. Only after the two-week window closes with no promotions does move 7 begin, one stage at a time. Net effect: by the time anything is deleted, Buddy will already feel bigger than it did with 19 modules.
